Аренда складских ячеек — Backend
Backend на ASP.NET Core 8, PostgreSQL, Clean Architecture.

Часть 1. Отчёт по проекту
1. Введение
Целью практической работы является разработка веб-приложения для аренды складских ячеек с backend-частью на REST API. Приложение позволяет гостям просматривать доступные склады и ячейки, клиентам — оформлять аренду, администраторам — управлять складами, ячейками, договорами аренды и ролями пользователей.

Задачи backend-части:

спроектировать доменную модель предметной области;
спроектировать структуру базы данных (ER-диаграмма);
реализовать REST API с разделением на слои согласно принципам Clean Architecture;
реализовать аутентификацию и авторизацию с разграничением ролей (гость, клиент, администратор);
покрыть основные сценарии (CRUD по складам, ячейкам и договорам аренды, смена статуса ячейки, оформление и расторжение аренды);
выполнить тестирование основных сценариев работы API.
Backend является самостоятельной частью, взаимодействующей с frontend исключительно по REST API, с передачей токена авторизации через HttpOnly-куку.

2. Обзор литературы
При выполнении backend-части проекта были изучены и проанализированы источники по проектированию архитектуры веб-приложений, работе с базами данных и построению REST API.

Основные направления анализа:

принципы Clean Architecture и разделение приложения на слои (Domain, Application, Infrastructure, Presentation);
подходы к проектированию REST API и выбору HTTP-методов, кодов ответов, структуры маршрутов;
проектирование реляционных баз данных и построение ER-диаграмм;
использование ORM Entity Framework Core и миграций Code First;
аутентификация и авторизация на основе ASP.NET Identity и JWT;
применение паттерна Result для обработки доменных ошибок без исключений;
использование value object'ов для проверки инвариантов домена.
Также были рассмотрены материалы по построению диаграмм: UseCase, диаграмма классов (UML), ER-диаграмма и UserStoryMap, что позволило согласовать backend-реализацию с общей проектной документацией команды.

Анализ литературы показал, что для данного проекта оптимальным является монолитная Clean Architecture с PostgreSQL и EF Core, поскольку это обеспечивает независимость доменной логики от инфраструктуры и упрощает дальнейшее развитие проекта.

3. Методология
Backend реализован на C# (.NET 8) с использованием монолитной Clean Architecture. Решение разделено на слои:

Domain — доменные сущности, value object'ы, интерфейсы репозиториев, доменные правила. Не зависит ни от одного другого слоя.
Application — сценарии использования (хендлеры), DTO запросов/ответов, интерфейсы репозиториев.
Infrastructure — реализация репозиториев на EF Core, конфигурации сущностей, подключение к PostgreSQL, интеграция ASP.NET Identity и генерация JWT.
Presentation (Api) — контроллеры, маршрутизация, Swagger, middleware, CORS.
Для представления результата операций вместо исключений используется паттерн Result (библиотека CSharpFunctionalExtensions): каждый доменный метод и хендлер возвращает Result с успешным значением либо доменной ошибкой (Error) с явным типом — Validation, NotFound, Conflict, Failure. Ошибки транслируются в HTTP-коды на уровне контроллеров через единый ответ-обёртку Envelope.

Идентификаторы сущностей и часть атрибутов оформлены как value object'ы (например, WareHouseId, StorageId, SizeOfStorage) с приватными конструкторами и статическими фабричными методами Create, что позволяет проверять инварианты в момент создания объекта. Изменение состояния сущностей выполняется только через их собственные доменные методы (Update, Patch, Reserve, Release), а не напрямую через сеттеры.

База данных — PostgreSQL, поднимается локально через Docker Compose. Миграции выполняются средствами EF Core (Code First) и применяются автоматически при старте приложения.

Для валидации входных данных используются FluentValidation (на уровне Application) и ручная валидация внутри доменных методов Create/Update (как основная защита инвариантов домена).

4. Проектирование данных
4.1. ER-диаграмма
В базе данных выделены следующие основные сущности:

Warehouse (склад) — Id, Name, Description, Address, Floor. Содержит набор ячеек.
StorageCell (складская ячейка) — Id, WarehouseId (FK), Number, Width/Height/Depth, SizeCategory, Price, Floor, Status (Free/Booked). Принадлежит одному складу.
RentalAgreement (договор аренды) — Id, StorageCellId (FK), ClientId (FK на пользователя Identity), StartDate, EndDate, TotalPrice.
AspNetUsers / AspNetRoles / AspNetUserRoles — таблицы ASP.NET Identity, создаются и обслуживаются средствами фреймворка.
Связи:

Warehouse (1) — StorageCell (N).
StorageCell (1) — RentalAgreement (N): ячейка за время своего существования может иметь несколько договоров аренды последовательно, после освобождения её можно сдать повторно.
Пользователь (1) — RentalAgreement (N): один клиент может оформить несколько договоров, что отражено полем ClientId у договора.
Поле Status у StorageCell хранит текущее состояние ячейки (свободна/забронирована) — денормализованное поле для быстрой проверки доступности без обращения к истории договоров. Освобождение ячейки происходит автоматически при расторжении договора.

4.2. Спецификация REST API
Аутентификация:

POST /auth/register — регистрация клиента, роль по умолчанию — Client
POST /auth/login — вход, токен возвращается в HttpOnly-куке access_token
POST /auth/logout — выход, удаление куки
Склады (Warehouse):

POST /warehouse — создать склад (администратор)
GET /warehouse — список складов (доступно всем, включая гостя)
GET /warehouse/{id} — карточка склада (доступно всем)
PUT /warehouse/{id} — полное обновление (администратор)
PATCH /warehouse/{id} — частичное обновление (администратор)
DELETE /warehouse/{id} — удаление (администратор)
Складские ячейки (StorageCell):

POST /storagecell — создать ячейку (администратор)
GET /storagecell — список ячеек (доступно всем)
GET /storagecell/{id} — карточка ячейки (доступно всем)
PUT /storagecell/{id} — полное обновление (администратор)
PATCH /storagecell/{id} — частичное обновление (администратор)
DELETE /storagecell/{id} — удаление (администратор)
POST /storagecell/{id}/reserve — забронировать ячейку (клиент, администратор)
Договоры аренды (RentalAgreement):

POST /api/rentalagreement — оформить аренду (клиент, администратор)
GET /api/rentalagreement — список договоров
GET /api/rentalagreement/{id} — карточка договора
PUT /api/rentalagreement/{id} — изменение сроков и стоимости
DELETE /api/rentalagreement/{id} — расторжение договора, автоматически освобождает ячейку
5. Роли и авторизация
Аутентификация построена на ASP.NET Identity (хранение пользователей, хэширование паролей, управление ролями) в сочетании с JWT. Токен генерируется при входе и регистрации и передаётся клиенту не в теле ответа, а в HttpOnly, Secure-куке с атрибутом SameSite=None — это защищает токен от чтения через JavaScript (XSS) и при этом позволяет работать с фронтендом на отдельном порту. JwtBearer-обработчик настроен на чтение токена именно из этой куки через событие OnMessageReceived.

В системе используются две Identity-роли — Administrator и Client. Роль «гость» отдельно не хранится и соответствует отсутствию авторизации: часть эндпоинтов (просмотр складов и ячеек) помечена как AllowAnonymous, остальные защищены атрибутом Authorize с указанием допустимых ролей на уровне контроллера или конкретного действия.

При первом запуске приложения в базе автоматически создаются роли Administrator и Client, а также учётная запись администратора по умолчанию, что обеспечивает возможность управлять ролями других пользователей сразу после развёртывания.

Матрица доступа:

Действие	Гость	Клиент	Администратор
Просмотр складов и ячеек	да	да	да
Создание/изменение/удаление склада	нет	нет	да
Создание/изменение/удаление ячейки	нет	нет	да
Бронирование ячейки	нет	да	да
Принудительное освобождение ячейки	нет	нет	да
Оформление договора аренды	нет	да	да
Просмотр и изменение договоров	нет	да	да
Управление ролями пользователей	нет	нет	да

6. Сравнительный анализ инструментов
СУБД — выбран PostgreSQL как бесплатное решение с открытым исходным кодом и зрелой поддержкой со стороны EF Core через провайдер Npgsql. MS SQL Server и MySQL рассматривались как альтернативы, но уступают по совокупности лицензионной модели и удобству развёртывания в Docker для учебного проекта.

Доступ к данным — выбран Entity Framework Core: позволяет описывать модель через Fluent API, поддерживает миграции Code First и конвертацию value object'ов в примитивные типы колонок (HasConversion). Dapper и ADO.NET были отклонены как избыточно трудозатратные при текущей модели домена.

Аутентификация — выбран ASP.NET Identity в связке с JWT, токен хранится в HttpOnly-куке, а не передаётся через заголовок Authorization — такой подход снижает риск кражи токена через XSS, при этом требует корректной настройки CORS с AllowCredentials и SameSite для работы с фронтендом на отдельном порту.

Валидация — FluentValidation на уровне Application плюс ручная валидация внутри доменных методов Create/Update как основная защита инвариантов домена.

CORS — политика настроена через явный список разрешённых источников (WithOrigins) с AllowCredentials — компромисс между удобством локальной разработки фронтенда и безопасностью, поскольку AllowAnyOrigin несовместим с передачей кук.

Документирование API — Swagger / OpenAPI для автоматической генерации документации и ручной проверки эндпоинтов, Postman — для ручного тестирования запросов и сценариев.

7. Выводы
В результате работы над backend-частью спроектирована доменная модель предметной области, построена структура базы данных, реализован REST API с разделением по слоям Clean Architecture. Добавлена система аутентификации и авторизации на базе ASP.NET Identity и JWT с передачей токена через HttpOnly-куку и тремя уровнями доступа — гость, клиент, администратор, разграниченными на уровне контроллеров через атрибут Authorize.

Архитектура позволяет независимо развивать бизнес-логику и инфраструктуру: смена СУБД или способа хранения токена не затрагивает доменный слой и сценарии использования. Использование паттерна Result и value object'ов обеспечивает явную обработку ошибок и защиту инвариантов домена независимо от уровня, на котором происходит обращение к сущности.

Основные задачи backend-части выполнены: реализованы CRUD-операции по складам, ячейкам и договорам аренды, смена статуса ячейки, оформление и расторжение аренды, разграничение прав доступа для гостя, клиента и администратора, настроен CORS для взаимодействия с отдельным frontend-приложением.

1. Поднять базу данных
В корне решения лежит docker-compose.yml:

docker compose up -d
Проверить, что контейнер поднялся:

docker compose ps
База будет доступна на localhost:5432, пользователь postgres, пароль postgres, база данных projectone (см. docker-compose.yml, при необходимости поменяйте).

2. Настроить конфигурацию
В ProjectOne/appsettings.Development.json (создайте, если его нет) укажите:

{
  "ConnectionStrings": {
    "Db": "Host=localhost;Port=5432;Database=projectone;Username=postgres;Password=postgres"
  },
  "Jwt": {
    "Issuer": "ProjectOne",
    "Audience": "ProjectOneClients",
    "Key": "замените-на-свой-секретный-ключ-минимум-32-символа",
    "ExpiresMinutes": 120
  }
}
Jwt:Key — обязательно смените на свой перед сдачей/публикацией, значение не должно попадать в открытый репозиторий в реальном проекте.

3. Применить миграции
Миграции применяются автоматически при старте приложения (см. Program.cs, db.Database.MigrateAsync()). Ручной запуск, если нужно применить их отдельно:

dotnet ef database update -p ProjectOne.Infrastructure -s ProjectOne
Создание новой миграции после изменения сущностей:

dotnet ef migrations add НазваниеМиграции -p ProjectOne.Infrastructure -s ProjectOne
4. Запустить API
dotnet run --project ProjectOne
По умолчанию API поднимется на https://localhost:44373 (или на порт, указанный в ProjectOne/Properties/launchSettings.json).

Swagger UI: https://localhost:44373/swagger

5. Роли и администратор по умолчанию
При первом запуске приложение автоматически создаёт две роли, если их ещё нет: Administrator, Client. Третья роль — «гость» — не хранится в базе, это неавторизованный доступ к общедоступным эндпоинтам.

Одновременно создаётся учётная запись администратора по умолчанию:

email: admin@projectone.local
пароль: Admin123!
Смените эти значения в Program.cs перед сдачей/публикацией проекта.

Управление ролями остальных пользователей выполняется через контроллер RoleController (POST /role/assign и т.д.), доступный только администратору.

6. Аутентификация
Токен выдаётся в виде HttpOnly-куки access_token после POST /auth/login или POST /auth/register — фронтенд не работает с токеном напрямую, достаточно отправлять запросы с credentials: 'include' (fetch) или withCredentials: true (axios).

Выход: POST /auth/logout — удаляет куку.

7. CORS
Список разрешённых origin'ов фронтенда задан в Program.cs (AddCors). При смене порта/адреса фронтенда — обновите WithOrigins(...). Поскольку токен передаётся в куке, политика обязательно использует AllowCredentials, что исключает AllowAnyOrigin — источники должны быть перечислены явно.

Возможные проблемы при запуске
Postgres не пускает по паролю — убедитесь, что контейнер поднят с тем же паролем, что указан в строке подключения; при смене пароля в docker-compose.yml для уже созданного контейнера нужно пересоздать volume (docker compose down -v && docker compose up -d).
Не собирается миграция из-за FluentValidation.AspNetCore — пакет не используется в проекте, валидация выполняется через FluentValidation + ручной вызов в хендлерах.
CORS-ошибка в браузере при логине с фронта — проверьте, что адрес фронтенда указан в WithOrigins, а запрос идёт с credentials: 'include'.
401/403 при обращении к защищённым эндпоинтам — проверьте, что кука access_token реально приходит с запросом (вкладка Network в браузере) и что роль в токене соответствует требуемой (можно посмотреть payload токена на jwt.io).
